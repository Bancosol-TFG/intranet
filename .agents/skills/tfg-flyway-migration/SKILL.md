# Flyway migrations

Flyway applies the database schema changes when the API starts. Hibernate runs with `ddl-auto: validate`: it only checks that the JPA entities match the schema and never changes it. Every schema change therefore needs a migration.

References: `docs/desarrollo/migraciones.md` and the ADRs about Flyway in `docs/adr/`.

## Location and names

Save the scripts in `api/src/main/resources/db/migration/`.

`application.yaml` sets lowercase prefixes, so the names are:

| Type | Format | Example |
| --- | --- | --- |
| Versioned | `v<YYMMDDHHmm>__<descripcion>.sql` | `v2610121530__crear_tabla_zones.sql` |
| Repeatable | `r__<descripcion>.sql` | `r__crear_vista_chains_activas.sql` |

- The version is the creation date and time as `YYMMDDHHmm`, in the `Europe/Madrid` time zone. Generate it with:

  ```sh
  TZ=Europe/Madrid date +%y%m%d%H%M
  ```

- Separate the version and the description with two underscores (`__`).
- Write the description in Spanish and `snake_case`, starting with a verb: `crear_tabla_zones`, `anadir_columna_phone_a_contacts`.
- `v1__crear_tabla_chains.sql` is the only legacy exception to this format. Do not use it as a naming model.
- Use repeatable migrations only for views, functions, or procedures. They have no version and run again whenever their checksum changes.

## Procedure

1. Confirm that the schema change has been agreed and check `model.dbml` for the expected tables and columns.
2. Generate the version and check that no other migration uses it, including on the remote `dev`:

   ```sh
   git fetch origin
   ls api/src/main/resources/db/migration/
   git ls-tree --name-only origin/dev api/src/main/resources/db/migration/
   ```

   If the version already exists, use another minute.
3. Create the script with only the change it needs. Use one migration per logical change and do not mix unrelated tables.
4. Update or create the JPA entity in the same change so that Hibernate validation passes.
5. Start the API against PostgreSQL (`docker compose up --build app`) and check the startup logs: Flyway must apply the migration and Hibernate must validate the schema without errors.
6. Check the applied row in `flyway_schema_history`, for example from Drizzle Studio at `http://localhost:5433`.
7. If the change affects documented conventions or the data model, update `model.dbml` or `docs/` in the same pull request.

## Schema conventions

Follow the style of the existing migrations:

- Tables in plural, lowercase, and `snake_case` (`chains`, `store_schedules`). Entities stay in singular.
- Columns in `snake_case`.
- Primary key: `id INTEGER GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY`.
- Audit and soft-delete columns, when the entity needs them:

  ```sql
  created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  updated_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  deleted_at TIMESTAMPTZ
  ```

- Name the constraints explicitly:
  - `pk_<table>` for primary keys, when not inline;
  - `uq_<table>_<columns>` for unique constraints;
  - `fk_<table>_<referenced_table>` for foreign keys;
  - `ck_<table>_<rule>` for check constraints;
  - `idx_<table>_<columns>` for indexes.
- Write SQL keywords in uppercase.
- Express data rules in the schema when possible (`NOT NULL`, `CHECK`, `UNIQUE`, foreign keys), such as `start_date < end_date` for campaigns.

## Rules

- Never edit, rename, or delete a migration that has been merged into `dev`. Flyway stores its checksum in `flyway_schema_history` and the API will not start if it changes. Fix it with a new migration.
- You may edit a migration that only exists on your branch. Then reset your local database, because Flyway has already recorded it locally:

  ```sh
  docker compose down
  rm -rf volumes/postgres_data
  docker compose up --build
  ```

  Deleting `volumes/postgres_data` erases all local data; ask the user before doing it.
- Do not use `ddl-auto` values other than `validate`, and do not create tables from code.
- Do not put environment-specific data or secrets in migrations.

## Integration order

The version reflects when the migration was written, not when it is merged. Flyway rejects a pending migration with a lower version than one that has already been applied, so the API fails to start if a pull request with an older migration is merged after one with a newer migration.

Before marking a pull request as ready, compare its versions with the latest one in `origin/dev`. If `dev` already has a newer migration, regenerate the version of your migration, which has not been merged yet, rename the file, and reset your local database.

The team has not yet agreed how to handle changes that modify or delete structures shared with other open pull requests. If a migration does so, point it out in the pull request description.
